Product surface (five /auth:… intents + handoff) follows the Design Baseline. Depth may be intentionally thin—see Baseline alignment before treating stubs as defects.

Domain objects

ObjectRole
Auth ContextWhat the IAM system looks like today (context.yaml)
ConstitutionDurable project rules (constitution.yaml)
Auth ChangeOne unit of decision work (changes/AUTH-YYYY-NNNN-…/)
DecisionExplicit architecture/technology choice (decisions.yaml, with type)
Decision PackageIndex + verification criteria (decision-package.yaml)
ContractConstraints + Verification implementers must honor (contract.md)
ReviewPost-export verification artifacts (reviews/…)

Knowledge Graph may exist as internal reasoning substrate; it is not a Phase 1 primary UX object.

Change id

Format: AUTH-YYYY-NNNN. The id is immutable. The folder may include a slug; renaming the slug does not change the id.

Decision Lock

Accepted Auth Decisions must not be silently inverted while coding agents implement via OpenSpec. authright review is the Phase 1 check.

Rule priority (reasoning)

  1. Critical security invariant
  2. Project Constitution
  3. Accepted decisions
  4. Industry best practice
  5. Agent preference

OpenSpec bridge

Overview

AuthRight Harness is the identity-security decision layer between your codebase and implementation. You understand the IAM reality, record durable decisions, export a package OpenSpec and coding agents can implement, then verify. Read this after [Getting started](/docs/getting-started) when you want the mental model on one screen. The long form is [Concepts](/docs/concepts).

Durable summary of the AuthRight Harness V1.0 Development Design Specification. Use this page (and [Baseline alignment](/docs/baseline-alignment)) as the in-repo product baseline. Depth may lag surface—see the alignment ledger for intentional thin-MVP deviations.
