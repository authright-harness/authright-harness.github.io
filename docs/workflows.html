Workflows

Common patterns using the design user-intent commands (colon product names). In Cursor type hyphen forms (/auth-scan); in Claude Code type colon forms (/auth:scan); in Codex type $authright-scan. Greenfield and brownfield are paths, not slash commands.

Happy path (greenfield)

Use this when the IAM model is still being shaped: new product, no identity estate yet, or the approach is not locked. /auth:change asks option questions before allocating AUTH-YYYY-NNNN and must not mark decisions accepted from the option answer alone. After required option chooses are answered, Decide continues in the same session. /auth:to-openspec intercepts unfinished work instead of bouncing to /auth:change when a gap is already actionable.

Chat skills /auth:change and /auth:doctor run their CLI loop when the opening utterance matches that command or the invoke has no extra text. A mismatched opening line (for example /auth:change + “explain what JWT is”) is answered in chat and does not create an Auth Change. The agent may hint another /auth: command; it must not auto-switch slash/skill. Later questions in an already-started change are digression — do not abandon that change. Terminal CLI does not refuse question-like intents. This gate does not apply to /auth:to-openspec.

Happy path (brownfield)

Use this when an identity system already exists and you need a scoped, grounded change (mixed IdPs, legacy sessions, partial OIDC, or first-party IdP gaps such as missing login methods or identity administration). Scan first so the change is anchored in current context and the IAM Domain Snapshot (including recommended identity_admin_scope object-breadth and identity_admin_ux completeness when admin signals exist). After scan, context.yaml fact lists are a projection of the Project Knowledge Graph; the Technology Registry catalog is not this project's facts. Decision Lock remains decisions.yaml. AuthRight is not an IdP runtime.

Diagnose

/auth:doctor / authright doctor when you need risk findings (requires a prior scan). Findings are observations, not Gaps — Gaps exist only when a Requirement is compared to CurrentState. Host agents may persist .authright/findings/agent-diagnosis.md; each new report copies ## Agent diagnosis from that overlay. Scan hypotheses with authority: llm_inference / H-LLM-* survive a later full scan. Overlays are inferences, not Decision Lock.

Document

/auth:doc (Cursor /auth-doc, Codex $authright-doc) writes an IAM document from the records already on disk. It does not update decisions, Design, or application configuration, and it has no terminal authright doc command. Each run writes a new UTC-timestamped file: .authright/docs/ for every Auth Change, or that change's docs/ directory when the invocation names one id. Earlier documents stay.

What not to do

  • Don't invent /auth:greenfield / /auth:brownfield / /auth:engineering slash commands
  • Don't ask Preserve/Evolve/Modernize during /auth:scan
  • Don't treat /auth:to-openspec as a fifth user-intent equal to scan/change/doctor/review
  • Don't treat /auth:doc as applying a solution or updating configuration — it only writes a new markdown file
  • Don't bounce from /auth:to-openspec to /auth:change when options are already answered or an unready change exists
  • Don't auto-run /auth:doctor because a /auth:change opening utterance looked like diagnosis (hint after chat is fine)
  • Don't type product slash commands in the terminal—How commands work

Scan (or empty) then /auth:to-openspec with no answered options and no Auth Change: run /auth:change. Export waits for an explicit continue confirm when nothing is pending — --ready is not silent.

How commands work

The one thing to know: AuthRight Harness has two kinds of commands, and they run in two different places.

Existing projects

AuthRight Harness is built for brownfield IAM: mixed IdPs, legacy sessions, partial OIDC, framework security that grew over years. You do not document the entire identity estate before the first useful change.
