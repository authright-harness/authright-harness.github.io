Existing projects

AuthRight Harness is built for brownfield IAM: mixed IdPs, legacy sessions, partial OIDC, framework security that grew over years. You do not document the entire identity estate before the first useful change.

Start with scan, not a blank encyclopedia

scan writes heuristic signals into .authright/context.yaml. Sparse repos get sparse context—that is expected. Enrich context and constitution as real changes force clarity.

One change at a time

Pick a concrete identity problem (SSO for one app surface, token audience fix, logout consistency). Create an Auth Change for that intent:

Keep the contract scoped. Export one OpenSpec package. Implement. Review. Then take the next slice.

What “good enough” context looks like

  • Named IdPs / protocols you actually touch
  • Where sessions/tokens are established today
  • Hard constraints in constitution.yaml (e.g. “no silent account linking”)
  • Explicit non-goals for this change

Avoid boiling the ocean: full protocol matrices, every microservice, or Knowledge Graph dumps are not Phase 1 user work.

Team adoption

  • Commit .authright/ so decisions travel with the repo
  • Prefer CLI for id allocation and export so humans share the same AUTH-YYYY-NNNN
  • Use Reviewing decisions before to-openspec so implementation doesn't invent auth policy in code review
